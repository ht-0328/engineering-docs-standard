# アンチパターン集

## この章の使い方

**レビューで見つけた症状から引く。** 症状 → なぜダメか → どう直すか、の順に並べている。

各項目は次の形である。

- **症状**: 何が起きているか
- **軸**: 品質6軸のどれに当たるか
- **Before / After**: 実例
- **なぜ良くなったか**

出典が示している実例には出典IDを付けた。付いていないものは、この標準が作った例である。

## A-01 一文に主題が3つ入っている

**軸: 明確性**

**Before**（`SRC-WRITE-003` 2.1）

```text
「HRTN CLOUD」はクラウド型ビジネスコミュニケーションツールで、ファイル管理、
プロジェクト管理、メッセンジャー、グループチャット機能をもっているため、資料や
プロジェクトの情報を共有し、コミュニケーションの迅速化を図ることができます。
```

**After**

```text
「HRTN CLOUD」はクラウド型ビジネスコミュニケーションツールです。
ファイル管理、プロジェクト管理、メッセンジャー、グループチャットなどの機能があります。
資料やプロジェクトの情報を共有し、コミュニケーションの迅速化を図ることができます。
```

**なぜ良くなったか**: 「何であるか」「何ができるか」「何の役に立つか」の3つが分かれた。読者は句点ごとに1つずつ理解を確定できる。

## A-02 「〜が」「〜ので」で文をつなぎ、要点が文末に沈む

**軸: 明確性・発見容易性**

**Before**（`SRC-WRITE-003` 2.3）

```text
チャットやメッセンジャー機能は、個人のユーザーを中心にネット時代の新しいコミュニ
ケーションツールとして普及していますが、データ管理面やセキュリティーの面で企業で
の利用には不安な点もあると考えられているのが実情です。（106字）
```

**After**

```text
チャットやメッセンジャー機能のビジネス利用は、データ管理やセキュリティーの面から
不安視されています。（49字）
```

**なぜ良くなったか**: 伝えたいこと（不安視されている）が主節に来た。**短くなったのは結果である。**

## A-03 状態の説明で終わり、読者が何をすればよいか分からない

**軸: 有用性**

**Before**（`SRC-WRITE-003` 3.2）

```text
セキュリティーソフトウェアの適切な利用により、外部からの攻撃のリスクを低減します。
```

**After**

```text
セキュリティーソフトウェアを適切に使用してください。外部からの攻撃を防ぐことがで
きます。
```

**なぜ良くなったか**: 行動（使用してください）と結果（防げます）が分かれた。動詞で書くと、読者は次に何をするか分かる。

## A-04 二重否定

**軸: 明確性**

**Before**（`SRC-WRITE-003` 3.3）

```text
フィルタリングソフトを適切に使わないと、青少年が有害サイトを閲覧することを防げま
せん。
```

**After**

```text
フィルタリングソフトを適切に使えば、青少年が有害サイトを閲覧することを防げます。
```

**なぜ良くなったか**: 読者が頭の中で否定を反転する作業が消えた。

## A-05 「など」で対象が確定しない

**軸: 正確性**

**Before**（`SRC-WRITE-003` 3.6）

```text
ドライバーやレンチなどを用意してください。
```

**After**

```text
ドライバーやレンチを用意してください。
```

**なぜ良くなったか**: 用意するものが確定した。「など」があると、読者は「ほかに何が要るのか」を調べる必要がある。

## A-06 注意文で、理由が先・指示が後

**軸: 有用性**

**Before**（`SRC-WRITE-003` 5.8）

```text
▲注意▲
一度削除を実行したファイルを復活することはできないので、ファイルを削除するときは、
確認メッセージとともに表示されるファイル名を確認してから実行してください。
```

**After**

```text
▲注意▲
ファイルを削除するときは、確認メッセージとともに表示されるファイル名を確認してから
実行してください。削除したファイルは復活できません。
```

**なぜ良くなったか**: 守るべき操作が先に来た。急いでいる読者は最初の一文だけで行動できる。

## A-07 動作主が無く、誰がやるのか決まらない

**軸: 明確性・有用性**

**Before**（`SRC-WRITE-004` 2-5）

```text
次回の打ち合わせは来週の水曜日くらいとの話になったが、その日は先方担当者の都合が
悪いかもしれないとの話になり、結局、その場では決められなかったため、後日調整しま
しょうという話になった。
```

**After**

```text
後日、当方○○が先方××様と日程調整することで合意した。
```

**なぜ良くなったか**: 誰が、誰と、何をするかが確定した。**議事録の目的は、次の行動を決めることである。**

## A-08 受け身で責任の所在がぼける

**軸: 明確性**

**Before**（`SRC-WRITE-004` 2-6）

```text
データベースの不具合によって、そのトラブルは引き起こされた。（30字）
```

**After**

```text
データベース不具合によりトラブル発生（18字）
```

**なぜ良くなったか**: 何が何を起こしたかが直接示された。

**ただし例外がある。** 手順書では、システム側の結果を受動態で書く（`SRC-WRITE-003` 3.4）。

```text
[保存] をクリックします。     ← 利用者の操作（能動）
設定が保存されます。          ← システムの反応（受動）
```

## A-09 曖昧語で期限も分量も決まらない

**軸: 正確性**

**Before**（`SRC-WRITE-001` 第2章）

```text
あの打ち合わせの内容、早めにまとめてください。
```

**After**

```text
昨日の営業部の打ち合わせの内容を、今日の17時までにA4用紙1枚にまとめてください。
```

**なぜ良くなったか**: どの打ち合わせか、いつまでか、どの分量かが決まった。

## A-10 専門用語が定義なしで出てくる

**軸: 明確性**

**Before**（`SRC-WRITE-001` 第2章）

```text
リスクマネジメントが必要です。
```

**After**

```text
問題が起きないよう事前に対策を考えましょう。
```

**なぜ良くなったか**: 読者が知らない語を使わずに、同じことを伝えた。

**注意**: これは「カタカナを消せ」という意味ではない。読者が知っている語なら、そのまま使う方が正確である。判断軸は [09-your-instincts.md](09-your-instincts.md#3-横文字カタカナ語が嫌い) にある。

## A-11 抽象的な分類だけで、具体が無い

**軸: 明確性**

**Before**（`SRC-WRITE-004` 2-4）

```text
メンバー間の人間関係が悪く、コミュニケーションが少ないと、システムプロダクトのうち、
共有が多い特性のあるプロダクトでミスが起こりやすくなります。
```

**After**

```text
メンバー間の人間関係が悪く、コミュニケーションが少ないと、システムプロダクトのうち、
共有が多い特性のあるプロダクト、たとえば、データベースや共通プログラムでミスが
起こりやすくなります。
```

**なぜ良くなったか**: 「共有が多い特性のあるプロダクト」が何を指すか決まった。**長くなったが、伝わるようになった。**

## A-12 読者が知らない前提を省いている

**軸: 有用性・正確性**

**Before**（`SRC-WRITE-004` 2-5）

```text
テストは○○日から、□□機能…略…××機能までを実施いただきたく存じます。
```

**After**

```text
テストは、構築してきたシステムの動作を確認するステップです。
あなたの業務を円滑に遂行させていくために、次のようにテストを実施させていただきます。
テストは○○日から、□□機能…略…××機能までを実施いただきたく存じますので、
ご理解いただきたくお願いいたします。
```

**なぜ良くなったか**: 読者（業務担当者）が「なぜ自分がやるのか」を理解できた。**書き手の常識は、読者の常識ではない。**

## A-13 件名と冒頭で同じことを2回言う

**軸: 明確性**

**Before**（`SRC-WRITE-003` 2.8）

```text
件名：「FinTech フォーラム」出展および参加報告

昨日、6月4日（月）から「FinTech フォーラム」が始まり、出展者としてブースを担当
しましたので、その状況についての報告とともに、他社ブースの内容も含めたフォーラム
全体の状況について報告させていただきます。
```

**After**

```text
件名：「FinTech フォーラム」出展および参加報告

昨日、6月4日（月）から始まった「FinTech フォーラム」のブースでの出展と、
全体の状況を報告いたします。
```

**なぜ良くなったか**: 件名で言ったことを繰り返さずに済んだ。読者は2回同じ話を読まされない。

## A-14 タイトルが「〜について」で中身が分からない

**軸: 発見容易性**

**Before**

```text
障害の件
打ち合わせについて
調査結果
```

**After**

```text
販売管理システム ファイル共有機能の障害報告と再発防止策
12/3 決済基盤リプレース 設計方針レビューのお願い
バッチ処理遅延の原因調査結果とインデックス追加の提案
```

**なぜ良くなったか**: 開かなくても中身が分かる。検索でも見つかる。

**出典**: `SRC-WRITE-003` 2.5

## A-15 見出しが「その他」「補足」「詳細」

**軸: 発見容易性**

**Before**

```markdown
## その他
## 補足
## 詳細
```

**After**

```markdown
## 制限事項と既知の不具合
## 本番環境と開発環境の差分
## バッチ再実行時のパラメータ一覧
```

**なぜ良くなったか**: 走査する読者（79%）が、この節を読むかどうか判断できる。

**出典**: `SRC-EXT-002`（"meaningful sub-headings (not 'clever' ones)"）

## A-16 手順の中に設計の背景が混ざる

**軸: 有用性**

**Before**

```markdown
## バッチの再実行手順

1. 管理画面にログインする。
   なお、この管理画面は2023年の基盤刷新でSpring Bootに移行しており、
   認証はOIDCに変更されている。旧来のBasic認証は廃止された。
2. ジョブ一覧から対象を選ぶ。
```

**After**

```markdown
## バッチの再実行手順

1. 管理画面にログインする。
2. ジョブ一覧から対象を選ぶ。

## 補足: 管理画面の認証方式

2023年の基盤刷新で Spring Boot に移行し、認証を OIDC に変更した。
旧来の Basic 認証は廃止されている。
```

**なぜ良くなったか**: 急いでいる読者は手順を追える。背景を知りたい読者は補足を読める。**情報は消していない。置き場所を変えただけである。**

**出典**: `SRC-EXT-004`（Diátaxis）

## A-17 事実と推定が混ざっている

**軸: 正確性**

**Before**

```text
バッチ処理が遅延しており、おそらくインデックスの不足が原因と思われるため、
インデックスを追加すれば解決する見込みです。
```

**After**

```text
【事実】8月27日 02:00 開始のバッチ処理が、通常の12分に対して47分かかった。
【推定】実行計画を確認したところ、テーブルAでフルスキャンが発生していた。
        インデックス不足が原因の可能性が高い。
【対策案】テーブルAの列Bにインデックスを追加する。効果は再実行で確認する。
```

**なぜ良くなったか**: 確認済みのことと未確認のことが分かれた。読者は「対策案はまだ検証されていない」と分かる。

**出典**: `SRC-WRITE-003` 7.4、`SRC-WRITE-004` 2-2

## A-18 条件が指示の後ろにある

**軸: 有用性**

**Before**

```text
[再実行] をクリックしてください。ただし、ジョブの状態が FAILED の場合に限ります。
```

**After**

```text
ジョブの状態が FAILED の場合は、[再実行] をクリックしてください。
```

**なぜ良くなったか**: 条件に当てはまらない読者が、実行してから気づくことがなくなった。

**出典**: `SRC-EXT-001`（"Put conditions before instructions, not after"）

## A-19 同じものを3通りの名前で呼ぶ

**軸: 一貫性**

**Before**

```text
ユーザーは管理画面から設定できます。
利用者が変更した内容は即座に反映されます。
顧客側で再設定する必要はありません。
```

**After**

```text
ユーザーは管理画面から設定できます。
ユーザーが変更した内容は即座に反映されます。
ユーザー側で再設定する必要はありません。
```

**なぜ良くなったか**: 読者が「別のものか」と考えずに済む。検索もできる。

**同義語で言い換えるのは、文章の技巧としては正しくても、技術文書では欠陥である。**

## A-20 リンク文字列が「こちら」

**軸: 発見容易性**

**Before**

```markdown
詳細は[こちら](...)を参照してください。
```

**After**

```markdown
詳細は[バッチ再実行の手順](...)を参照してください。
```

**なぜ良くなったか**: リンクだけを拾って読む読者にも行き先が分かる。

**出典**: `SRC-EXT-001`、`SRC-EXT-005`

## A-21 コピーしても動かないコマンド

**軸: 有用性・正確性**

**Before**

```markdown
以下を実行してください。

docker compose down -v
```

**After**

````markdown
開発環境のデータベースを初期化する。**この操作でボリュームが削除され、
開発用データはすべて消える。** 本番環境では実行しない。

```bash
docker compose down -v
```

実行後、`docker volume ls` に対象のボリュームが表示されないことを確認する。
````

**なぜ良くなったか**: 言語が指定され、前提と結果と危険が書かれた。**読者が実行してよいかを判断できる。**

## A-22 時点に依存する語が入っている

**軸: 保守性**

**Before**

```text
現在はバッチの並列実行に対応していません。今後対応予定です。
```

**After**

```text
v2.4 時点では、バッチの並列実行に対応していない。
対応の予定は未定である（2026-08-28 確認）。
```

**なぜ良くなったか**: 1年後に読んでも、いつ時点の情報かが分かる。

**出典**: `SRC-EXT-001`（timeless documentation）

## A-23 見出しの直後に本文が無い

**軸: 発見容易性**

**Before**

```markdown
## 再発防止策

### 短期対策

#### 監視の追加
```

**After**

```markdown
## 再発防止策

短期と長期に分けて示す。短期対策は9月中に、長期対策は12月末までに完了する。

### 短期対策

同じ障害を検知できるようにする。実装は2件である。

#### 監視の追加
```

**なぜ良くなったか**: 走査する読者が、その節を読むかどうかを最初の1文で判断できる。

**出典**: `SRC-EXT-001`（"Don't use empty headings"）

## A-24 箇条書きの型が途中で崩れる

**軸: 明確性**

**Before**（`SRC-EXT-001`）

```text
1. Instantiate the Froobus class.
2. Invoke the Froobus.Salmonella() method.
3. The process stalls.
```

**After**

```text
1. Froobus クラスを生成する。
2. Froobus.Salmonella() メソッドを呼び出す。
3. 処理が停止することを確認する。
```

**なぜ良くなったか**: 3つ目も指示の形になった。**手順の中に結果の説明が混ざっていた。**

## A-25 図に凡例が無く、色の意味が分からない

**軸: 明確性**

**Before**: ノードが15個あり、青と赤と緑で塗り分けられているが、色の意味がどこにも書かれていない図。

**After**: ノードを10個以下に減らし、色を2色に絞り、図の下に「青＝同期処理、橙＝非同期処理」と書く。

**なぜ良くなったか**: 色に意味を持たせるなら凡例が要る。ノード数の上限は `SRC-WRITE-002` 8.5.5 が10としている。

**判断**: その図を消したとき、文章だけで同じことが伝わるなら、図は要らない。
