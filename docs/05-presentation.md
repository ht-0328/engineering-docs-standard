# 見せ方のルール

## 結論

**情報の形に合わせて器を選ぶ。** 器が合っていないと、正しい内容でも読み取れない。

| 情報の形 | 使う器 |
|---|---|
| 一つのことを述べる | 文 |
| 並列する項目 | 箇条書き |
| 順序のある作業 | 番号付きリスト |
| 同じ軸で複数を比べる | 表 |
| 数値の比較・推移 | グラフ |
| 関係・階層・流れ | 図 |
| 実行できるもの | コードブロック |
| 情景・実物 | 写真 |

出典は `SRC-WRITE-003` 6.6–6.7、`SRC-EXT-001`、`SRC-WRITE-002` 第7〜8章である。

---

## P-01 箇条書きは並列するものだけに使う

**規範度: 必須**

**なぜ（明確性）**: 箇条書きは「これらは同じ種類のものだ」という主張である。原因と手順と結論を同じリストに混ぜると、読者は関係を誤解する。

**守ること**

| # | 規則 | 出典 |
|---|---|---|
| 1 | 項目の文法・粒度・文末をそろえる（並列性） | `SRC-EXT-001` |
| 2 | 最初の項目が型を決める。以降はその型に従う | `SRC-EXT-001` |
| 3 | 句点（。）を付けるか付けないかを、リスト内で統一する | `SRC-EXT-003` 1.1.3、`SRC-WRITE-003` 4.7 |
| 4 | 7項目以内にする | `SRC-WRITE-003` 4.7 |
| 5 | 具体的な見出しを付ける | `SRC-WRITE-003` 4.7 |
| 6 | 直前に、コロンで終わる導入文を置く | `SRC-EXT-001` |
| 7 | 順序に意味があれば番号付き、なければ黒丸 | `SRC-EXT-001` |
| 8 | 番号付きリストの各項目は動詞で始める | `SRC-EXT-001` |

**並列性が崩れた例**（`SRC-EXT-001` より）

```text
- Broccoli inspires feelings of love or hate.
- Potatoes taste delicious.
- Cabbages.
```

3つ目だけが完全な文になっていない。読者は「書き忘れか」と考える。

**番号付きリストの型が崩れた例**

```text
1. Instantiate the Froobus class.
2. Invoke the Froobus.Salmonella() method.
3. The process stalls.        ← 指示ではなく状態の説明
```

3つ目は読者への指示ではない。**手順の中に結果が混ざっている。** 分けるか、「〜を確認する」と指示の形にする。

**7項目を超えたときの対処**（`SRC-WRITE-003` 4.7）

1. グループ化して全体を分ける
2. 優先度の高い項目に絞る

## P-02 表は、同じ軸で複数を比べるときだけ使う

**規範度: 推奨**

**なぜ（明確性）**: 表は「行どうしを比べてほしい」という主張である。比較軸がそろっていない表は、ただの箱である。

**守ること**

| # | 規則 | 出典 |
|---|---|---|
| 1 | 列見出しに意味のある名前を付ける | `SRC-EXT-001` |
| 2 | 各列の中で粒度と形式をそろえる | `SRC-EXT-001` |
| 3 | **セルに2文を超える文章を入れない。** 超えたら別の形式を検討する | `SRC-EXT-001` |
| 4 | 5〜6列を超えたら分割を検討する | `SRC-WRITE-002` 7.8.3 |
| 5 | 空セルでもパイプを省略しない。列数をそろえる | `SRC-WRITE-002` 7.8.3 |
| 6 | セル内のパイプは `\|` と書く（インラインコード内でも必要） | `SRC-WRITE-002` 7.8.5 |

**表にしてはいけないもの**: 長文の説明。比較しない情報の羅列。

## P-03 図は、言葉で書くと長くなる関係を示すときに使う

**規範度: 推奨**

**なぜ（明確性）**: 図は装飾ではない。**文章で書くと長くなる関係を、一度に見せるための道具である。**

**図の種類の選び方**

| 示したいもの | 図の種類 | Mermaid の記法 |
|---|---|---|
| 処理の流れ、条件分岐 | フローチャート | `flowchart` |
| システムどうしのやり取りと順序 | シーケンス図 | `sequenceDiagram` |
| 状態の変化と遷移条件 | 状態遷移図 | `stateDiagram-v2` |
| データの構造と関連 | ER図 | `erDiagram` |
| クラスの構造 | クラス図 | `classDiagram` |
| 階層構造 | マインドマップ | `mindmap` |
| 割合 | 円グラフ | `pie` |
| 日程 | ガントチャート | `gantt` |

**守ること**

| # | 規則 | 出典 |
|---|---|---|
| 1 | **ノードが10を超えたら分割する。** または画像にする | `SRC-WRITE-002` 8.5.5 |
| 2 | ノードIDは半角英数字にし、意味のある名前を付ける（`A` ではなく `login`） | `SRC-WRITE-002` 8.5.5、8.5.7 |
| 3 | 流れの向きは上から下、または左から右にする | `SRC-WRITE-002` 8.5.3 |
| 4 | 図だけで完結させない。図の前後に、図が何を示すかを文で書く | `SRC-WRITE-003` 6.7 |
| 5 | 写真と文字を重ねない | `SRC-WRITE-003` 6.7 |

**図が必要かどうかの判断**: その図を消したとき、文章だけで同じことが伝わるなら、図は要らない。**逆に、図が無いと説明が3段落必要になるなら、図を入れる。**

図の作り方（Mermaid / draw.io / 手書きSVG の使い分け）は [adr/ADR-001-diagram-tool.md](adr/ADR-001-diagram-tool.md) に記録している。

## P-04 コードは実行できる形で書く

**規範度: 必須**

**なぜ（有用性・正確性）**: コピーして動かないコード例は、無いより悪い。読者は動かない理由を探して時間を失う。

**守ること**

| # | 規則 |
|---|---|
| 1 | フェンス形式（```）を使い、**言語名を必ず指定する** |
| 2 | 前提（環境、権限、事前に必要な状態）を書く |
| 3 | 期待される出力を示す |
| 4 | 破壊的な操作には、実行前に何が起きるかを書く |
| 5 | プロンプト記号（`$`）を付けるなら、出力と混ぜない |
| 6 | 固有名詞を不必要にインラインコードにしない |

**Before**

```text
以下を実行してください。

docker compose down -v
```

**After**

````text
開発環境のデータベースを初期化する。**この操作でボリュームが削除され、
開発用データはすべて消える。** 本番環境では実行しない。

```bash
docker compose down -v
```

実行後、`docker volume ls` に対象のボリュームが表示されないことを確認する。
````

## P-05 リンクは、リンク先が分かる言葉にする

**規範度: 必須**

**なぜ（発見容易性）**: 「こちら」は、周囲の文を読まないと何のリンクか分からない。走査する読者には届かない。

<!-- doclint-disable link_text broken_local_link bare_url_link -->

| 使わない | 直した |
|---|---|
| 詳細は[こちら](...) | 詳細は[バッチ再実行の手順](...)にある |
| [この記事](...)を参照 | [Diátaxis の品質の定義](...)を参照 |
| `https://example.com/very/long/url` をそのまま貼る | [Google developer documentation style guide](...) |

<!-- doclint-enable -->

`SRC-EXT-001` の規則である。

> "Write link text that makes sense without the surrounding text. Don't use phrases such as _this document_, _this article_, or _click here_."

**出典**: `SRC-EXT-001`、`SRC-WRITE-002` 7.4.3、`SRC-EXT-005`

## P-06 Markdown の書き方をそろえる

**規範度: 推奨**

**なぜ（一貫性・保守性）**: 記法が揺れると差分が読みにくくなり、変換結果も環境ごとに変わる。

**この標準で採る書き方**（`SRC-WRITE-002` 第7〜8章に準拠）

| 対象 | 決めごと |
|---|---|
| 見出し | ATX形式（`#`）。`#` の後にスペース1つ。前後に空行。レベル1は文書に1つだけ。レベルを飛ばさない |
| 見出しの深さ | レベル4まで。5〜6が必要なら文書を分割する |
| 箇条書き | `-` に統一。前後に空行。ネストは2階層まで（深くても3階層） |
| 強調 | 太字は `**`。**太字を見出しの代わりに使わない**。日本語では斜体を使わず太字を使う |
| コードブロック | フェンス形式。言語名を必ず指定。前後に空行 |
| 表 | 先頭・末尾にパイプ。全行の列数をそろえる。前後に空行 |
| リンク | 少数ならインライン。同じURLを繰り返すなら参照リンク |
| 画像 | 代替テキストを必ず書く。相対パスを使う |
| 水平線 | `---`。多用しない。前に空行を入れる（無いとSetext見出しになる） |
| 段落 | 空行で分ける。行末の2スペースによる改行は使わない |

**よくある誤り**（`SRC-WRITE-002` の「よくある間違いと対処法」より抜粋）

| 誤り | 対処 |
|---|---|
| `#見出し`（`#` の後にスペースが無い） | `# 見出し` にする |
| 見出しレベルを飛ばす | 1レベルずつ増やす |
| `** 太字 **`（記号と文字の間にスペース） | 記号を文字に隣接させる |
| リストの前後に空行が無い | 空行を入れる |
| `[text] (URL)`（`]` と `(` の間にスペース） | 連続させる |
| 画像記法の `!` を忘れる | `![代替テキスト](URL)` にする |
| 表セル内の `|` をエスケープしない | `\|` にする |
| MermaidのノードIDに日本語を使う | IDは半角英数字、表示文字列は括弧内に書く |

**これらは機械で検出できる。** 人間のレビューで指摘する項目ではない。

## P-07 プラットフォームの差を前提にする

**規範度: 推奨**

**なぜ（正確性）**: Markdown には方言がある。GitHub で書いたものが Slack や Qiita でそのまま表示されるとは限らない。

`SRC-WRITE-002` は各記法に「方言対応表」を付けている。特に差が大きいのは次である。

| 記法 | 差の例 |
|---|---|
| 強調 | Slack・Teams は `*太字*`、GitHub 等は `**太字**` |
| アラート | GitHub、Qiita、Zenn でそれぞれ記法が違う |
| Mermaid | 対応しない環境がある。その場合は画像にする |
| 折りたたみ | GitHub は `<details>`、Zenn は独自記法 |
| ハイライト | `==...==` は Obsidian 専用 |
| 目次の自動生成 | `[:contents]` ははてなブログ専用 |

**移植性を重視する文書では、標準的な記法だけを使う。** 目次はアンカーリンクで手動作成する。

**出典**: `SRC-WRITE-002` 各節「方言対応表」

## P-08 機械で直せるものは機械に任せる

**規範度: 推奨**

**なぜ（保守性）**: 表記の指摘に人間の時間を使うと、内容と構造のレビューまで届かない。

`SRC-WRITE-002` 第6章は markdownlint の使い方を示している。日本語文書では次の調整が要る。

```json
{
  "default": true,
  "MD013": false,
  "MD024": { "siblings_only": true },
  "MD033": {
    "allowed_elements": ["br", "details", "summary", "img"]
  }
}
```

| ルール | 既定の動作 | 調整 | 理由 |
|---|---|---|---|
| `MD013` | 1行80文字超で警告 | **無効化** | 日本語文の途中でソフト改行すると、表示時に半角スペースが入って不自然になる |
| `MD024` | 重複見出しをすべて警告 | `siblings_only: true` | 章ごとの「まとめ」等は自然に重複する |
| `MD033` | HTMLタグを警告 | 必要なタグを許可 | `<details>` 等はMarkdownだけでは表せない |

**この標準では、markdownlint に加えて日本語固有の検査を [tools/doc_lint.py](../tools/doc_lint.py) で行う。** 文長、読点の数、文体の混在、曖昧語、ひらがな開き、用語の揺れなどである。

**ただし、[01-what-is-good.md](01-what-is-good.md#測れる品質と測れない品質) に書いたとおり、チェッカーを通ったことは品質の証明ではない。**
