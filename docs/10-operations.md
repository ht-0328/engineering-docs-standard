# 運用

## 結論

**書き上げた瞬間から、文書は古くなり始める。**

`SRC-EXT-005` は、この問題をはっきり言い切っている。

> "Consider incorrect documentation to be worse than missing documentation."

**誤った文書は、文書が無いことより悪い。** 読者は書いてあることを信じて作業するからである。無ければ人に聞く。あれば信じて間違える。

したがって、運用の目的は1つである。**文書が古くなったことに気づける状態を保つ。**

---

## O-01 文書をコードと同じ場所・同じ手順で扱う

**規範度: 推奨**

**なぜ（保守性）**: 別の場所に置くと、コードを直したときに文書を直し忘れる。

`SRC-EXT-005` の docs as code は、5つの要素で定義されている。

| 要素 | このリポジトリでの実装 |
|---|---|
| 課題管理 | 文書の不備を課題として登録する |
| バージョン管理（Git） | `docs/` を Git で管理する |
| プレーンテキストの記法 | Markdown を正本にする |
| コードレビュー | 文書の変更もレビューを通す |
| 自動テスト | [tools/doc_lint.py](../tools/doc_lint.py) を通す |

`Nearby` 原則も同じことを求めている。

> "Store sources as close as possible to the code which they document."

**出典**: `SRC-EXT-005`

---

## O-02 最終確認日と保守責任者を持たせる

**規範度: 必須**

**なぜ（保守性）**: 「いつ時点の情報か」が分からない文書は、読者が信じてよいかどうかを判断できない。

**「最終更新日」ではなく「最終確認日」にする。** 更新が無くても、内容がまだ正しいと確認したことを示せる。

```markdown
| 項目 | 内容 |
|---|---|
| 保守責任者 | 決済基盤チーム |
| 最終確認日 | 2026-08-28 |
| 次回確認予定 | 2026-11-28 |
```

**確認の間隔の目安**

文書は2種類に分かれる。**現在の状態を表す文書**と、**ある時点の記録**である。この2つは扱いが違う。

| 種類 | 文書 | 確認の間隔 |
|---|---|---|
| 現在の状態を表す | 運用手順書（実行される） | 3か月 |
| 現在の状態を表す | API仕様書 | 変更のたび |
| 現在の状態を表す | **設計書（現行構成を説明するもの）** | **6か月** |
| 現在の状態を表す | README | 3か月 |
| ある時点の記録 | ADR | 確認不要 |
| ある時点の記録 | 障害報告書 | 確認不要 |
| ある時点の記録 | 議事録 | 確認不要 |

**設計書を「確認不要」に入れてはいけない。** 現行の構成や制約を説明する設計書は、システムが変わるたびに古くなる。古い設計書を信じた読者は、存在しない制約に合わせて作業する。

### ある時点の記録の扱い

**内容は書き換えない。追記する。**

| 起きたこと | やること |
|---|---|
| 決定が変わった | 新しい記録を作る。古い記録の冒頭に「置き換え済み: ADR-012 を参照」と追記する |
| 記録した事実が誤っていた | **訂正する。** ただし、いつ何をどう訂正したかを追記する。誤ったまま残さない |
| 表記の誤りが見つかった | 直してよい |

**「更新しない」は「誤りを残す」という意味ではない。** 正確性（品質6軸の3）は保守性より優先される。訂正の履歴を残すことで、両方を満たせる。

**出典**: `SRC-EXT-005`（Current）。`SRC-EXT-006`（ADR）は「1つの決定とその根拠を記録する」と定義するだけで、**記録を書き換えてはいけないとは書いていない。** 上の訂正の扱いは**出典なし・運用上の取り決め**である。

## O-03 時点に依存する語を書かない

**規範度: 必須**

**なぜ（保守性）**: 「現在は未対応です」は、書いた翌日から意味が変わる。読み手はいつの「現在」か分からない。

`SRC-EXT-001` が避けるべき語を挙げている。日本語版を作った。

| 避ける語 | 書き換える |
|---|---|
| 現在は、現時点では、今のところ | 日付、または版数 |
| 今後、将来的に | 予定があるなら日付。無いなら書かない |
| 最新の、新しい | 版数 |
| 近日、まもなく | 日付。決まっていないなら書かない |
| 従来の、以前は | 版数と、その版での挙動 |

**Before**

```text
現在はバッチの並列実行に対応していません。今後対応予定です。
```

**After**

```text
v2.4 時点では、バッチの並列実行に対応していない。
対応の予定は未定である（2026-08-28 確認）。
```

原則の記述はこうである。

> "Timeless documentation focuses on how the product works right now—not on how it has changed from previous versions, and not how it might change in the future."

**これは `doc_lint` の `timeless` ルールが検出する。**

**出典**: `SRC-EXT-001`

## O-04 同じことを2つの文書に書かない

**規範度: 必須**

**なぜ（保守性・正確性）**: 同じ情報が2か所にあると、片方が必ず古くなる。そして、どちらが正しいか読者には分からない。

`SRC-EXT-005` の `Unique` 原則である。

> "Eliminate content overlap between separate sources."

**ただし、1つの文書の中では重複を許す。** これは `ARID` 原則である。

> "Accept (some) Repetition In Documentation."

**層を混同しないこと。**

| 層 | 方針 |
|---|---|
| 1つの文の中 | 冗長は削る（`SRC-WRITE-003` 2.8） |
| 1つの文書の中 | 読者が1か所で用を足せるよう、必要な重複は許す（ARID） |
| 文書と文書の間 | 重複させない。片方をリンクにする（Unique） |

**エンジニアが最も間違えやすい点である。** コードの DRY をそのまま文書に持ち込むと、リンクだらけで読めない文書ができる。

**出典**: `SRC-EXT-005`

## O-05 消すことも品質改善である

**規範度: 推奨**

**なぜ（保守性・正確性）**: 誰も保守しない文書を残しておくのは、善意ではなく害である。

**消す判断の基準**

| 状態 | 判断 |
|---|---|
| 保守責任者がいない | 引き受け手を探す。見つからなければ消す |
| 最終確認日から1年以上経ち、内容の正しさを誰も確認できない | 消す。または「保守されていない」と冒頭に明記する |
| 同じ内容の新しい文書がある | 消して、新しい文書へのリンクだけを残す |
| 過去の時点の記録（ADR、障害報告、議事録） | **消さない。** 時点の記録は古びない |

**消すときは、消したことが分かるようにする。** リンク切れは読者を困らせる。移動先か、消した理由を残す。

**出典**: `SRC-EXT-005`（Current）。消す判断の具体的な基準は**出典なし・運用上の取り決め**である。

## O-06 機械で判定できることは自動化する

**規範度: 推奨**

**なぜ（保守性）**: 表記の指摘に人の時間を使うと、内容と構造のレビューまで届かない。

**このリポジトリでの自動化**

| 対象 | 道具 | 実行 |
|---|---|---|
| 日本語の文書ルール | [tools/doc_lint.py](../tools/doc_lint.py) | `docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/w" -w /w edocs-tools python tools/doc_lint.py` |
| Markdown の記法 | markdownlint（`SRC-WRITE-002` 6.2 の設定） | 編集環境の拡張機能、または `markdownlint-cli2` |
| 図の書き出し | [tools/export_diagrams.sh](../tools/export_diagrams.sh) | `bash tools/export_diagrams.sh` |
| サイトの生成 | [tools/build_site.py](../tools/build_site.py) | `docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/w" -w /w edocs-tools python tools/build_site.py` |

**自動チェックで判定できないこと**

- 読者に合っているか
- 結論が妥当か
- 事実が正しいか
- 必要な情報が欠けていないか

**したがって、`doc_lint` を通ったことを品質の証明にしてはいけない。** これは [01-what-is-good.md](01-what-is-good.md#測れる品質と-測れない品質) に書いたとおりである。

**出典**: `SRC-EXT-005`、`SRC-WRITE-002` 6.2、`SRC-EXT-004`

## O-07 未解決の印を残したまま公開しない

**規範度: 必須**

**なぜ（正確性・有用性）**: `TBD`、`TODO`、`未定` が残った文書を読んだ読者は、そこが「まだ決まっていない」のか「書き忘れ」なのか判断できない。決まっていないなら、誰がいつ決めるのかを知りたい。

**やること**

`TBD` の代わりに、次のどちらかを書く。

1. `（未記入）` と書き、**誰がいつまでに埋めるかを未決事項の節に書く。**
2. その節を削り、扱わない理由を B-04（扱わないことを書く）に従って書く。

**Before**

```markdown
## 性能要件

応答時間: TBD
同時接続数: TODO
```

**After**

```markdown
## 性能要件

| 項目 | 値 | 状態 |
|---|---|---|
| 応答時間 | （未記入） | 【未決】性能試験の結果待ち。担当: 山田、回答期限: 2026-09-10 |
| 同時接続数 | 200 | 【決定】 |
```

**効果**: 読者は「まだ決まっていない」と「誰に聞けばよいか」が分かる。

**これは `doc_lint` の `unresolved_marker` が検出する。**

**出典**: **出典なし・運用上の取り決め**。
