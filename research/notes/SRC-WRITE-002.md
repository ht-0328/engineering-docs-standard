# SRC-WRITE-002 『ITエンジニアのためのMarkdown実践入門』

## 1. 記法ごとの「推奨する書き方」

| 記法・所在 | 推奨ルール | 制約・注意 |
|---|---|---|
| 見出し（7.1.3） | レベル1は文書タイトルとして1つだけ。レベル2＝章、3＝節、4＝必要な小節。5～6が必要なら分割を検討。ATX形式に統一。前後に空行。レベルを飛ばさない。簡潔なラベルにし、文や句読点を置かない | 番号の自動付与やフォント・色の指定はできない |
| 文字装飾（7.2.3） | 太字・斜体はアスタリスク形式に統一。強調は最小限。太字を見出し代わりにしない。日本語の斜体は控えめにし、強調は太字を使う | 標準Markdownは太字・斜体・取り消し線のみ。下線、色、サイズ、ハイライト、上付き・下付きは標準記法にない |
| リスト（7.3.3） | 箇条書きは `-` に統一。前後に空行。インデントはスペース。継続行はテキスト開始位置に揃える。ネストは2階層、深くても3階層まで。本書では同階層のインデントを2スペースに統一 | リスト記号の見た目は変更できない。装飾目的のインデントは構造として誤解される |
| リンク（7.4.3） | 少数ならインラインリンク。同じURLを繰り返す、またはリンクが多い文書では参照リンク。リンクテキストは「こちら」ではなくリンク先が分かる具体的な語にする | `target="_blank"` や `rel="nofollow"` 等の属性は指定できない |
| 画像（7.5.3） | 内容を端的に表す代替テキストを必ず書く。装飾画像だけ空を許容。代替テキストは1文程度。プロジェクト内では相対パス。内容が分かるファイル名。大きすぎる画像はリサイズ | サイズ・配置・キャプションは標準記法では指定できない |
| 引用（7.6.3） | `>` の後にスペース1つ。前後に空行。ネストは2段階まで | 出典専用の記法はないため、引用内または直後にテキストで書く |
| コードブロック（7.7.3） | フェンス形式に統一し、言語名・形式名を指定する。前後に空行。インラインコードは短いコードだけ。固有名詞を不必要にインラインコード化しない | 標準記法では行番号、特定行の強調、ファイル名ラベルを指定できない |
| 表（7.8.3） | 先頭・末尾のパイプを付ける。全行の列数を揃え、空セルでもパイプを省略しない。前後に空行。ソース上も列を揃える。5～6列を超えたら分割を検討 | セル結合、セル内改行、表の入れ子は標準記法ではできない |
| 水平線（7.9.3） | `---` に統一。多用せず、大きな話題の切り替わりに限定する。通常のセクション区切りには見出しを使う | 太さ・色・破線等の見た目は変更できない |
| 段落と改行（7.10.4） | 段落は空行で分ける。ハード改行は住所・署名欄等に限定。ハード改行には、見えない行末2スペースよりバックスラッシュを推奨。連続空行は入れない | 段落間余白、改ページ、通常の字下げは指定できない。字下げが必要なら本文は全角スペースを挙げる |
| 脚注（8.1.3） | `[^reference]` など意味のある識別子を付ける。脚注には補足・参照情報だけを置き、理解に不可欠な内容は本文に書く。多用しない | 対応プラットフォームが限定される |
| アンカーリンク（8.2.3） | 同じ見出しテキストを複数使わない。重複すると2つ目以降に連番が付き、リンク指定が煩雑になる | 英語見出しは通常、小文字化し、スペースをハイフンに変換する。見出し変更時はリンクも更新する |
| 目次自動生成（8.3.2） | ポータビリティを重視する文書では、プラットフォーム固有の自動目次記法ではなく、アンカーリンクによる手動目次を使う | `[:contents]` ははてなブログ専用 |
| アラート・コールアウト（8.4.3） | 内容に応じてNOTE、TIP、WARNING等を使い分ける。簡潔にし、長文は本文へ移してアラートには要約を書く。多用しない | 記法がプラットフォームごとに異なる |
| Mermaid（8.5.5） | 図を単純に保ち、ノードが10を超えるなら分割または画像化を検討。`A`、`B` ではなく `login`、`validate` のような意味のあるID。図の種類の次から定義行を4スペースでインデント | レイアウトは自動決定される。非対応環境では画像化する |
| 数式（8.6.3） | 短い式はインライン、独立した定理・長い式はブロック。ブロック数式の前後に空行。複雑な数式は表の外に置く | 記法・対応状況がプラットフォームごとに違う |
| 折りたたみ（8.7.3） | `<summary>` に展開内容が分かる短く明確なラベルを付ける。重要情報は折りたたまない | GitHub等は `<details>`、Zennは独自記法。対応差が大きい |
| HTML埋め込み（8.8.3） | Markdownで表現できるものはMarkdownを優先し、HTMLは最小限。`alt` 属性や適切な見出しレベルなどアクセシビリティを守る | プラットフォームがタグや `style` 属性を削除する場合がある |
| エスケープ（8.9.3） | 記号が多い内容は個別エスケープよりコードブロック・インラインコードを使う。必要な箇所だけエスケープ。表内のパイプは必ず `\|` | バックスラッシュエスケープの対応状況に差がある |
| その他（8.10.1～8.10.4） | ハイライトの `==...==` はObsidian専用。他環境では対応する場合のみ `<mark>`。絵文字は複数環境で使うならUnicode直接入力が確実。Base64画像は可読性が下がるため数KB以下の小アイコンに限定。Front Matterはファイルの1行目に置く | ハイライト、絵文字ショートコード、Base64画像、Front Matterはいずれも対応差が大きい |

### 比較観点

方言対応表は、各プラットフォームの主要なテキスト入力欄において、各記法・書き方が次のどれに該当するかを比較している（「方言対応表の見方」）。

- `○`：標準的な記法で対応
- `×`：非対応
- `△`：条件付き、制限付き、または部分対応

比較対象には、単なる記法名だけでなく、次のような書き方の差も含まれる。

- 見出しレベル、Setext形式
- アスタリスク／アンダースコア、取り消し線
- リスト記号、タスクリスト、ネスト、継続行
- インライン／参照／タイトル付きリンク
- 画像、HTML画像、プラットフォーム独自の埋め込み
- コードフェンス、言語指定、ファイル名、diff
- ソフト改行・ハード改行
- 脚注、アンカー、自動目次、アラート
- Mermaid、数式、折りたたみ、HTML、エスケープ
- ハイライト、絵文字、Base64画像、Front Matter

GitHub列は、厳密なGFM仕様だけでなく、GitHub独自のアラートや絵文字機能も含む「GitHubプラットフォーム全体」の対応状況としている。GFM互換ならGitHub列相当の動作が期待できる一方、CommonMark対応だけの場合は、表・タスクリスト・取り消し線等が使えない可能性がある（「方言対応表の見方」）。

## 4. markdownlint

### 位置づけ

markdownlintは50以上のルールでMarkdownをリアルタイムに検査し、見出し前後の空行不足やリストインデントの不揃いなどを警告する。第7・8章の「推奨する書き方」は、この推奨ルールを基礎としている（6.1.2、6.2）。

### 設定ファイル

プロジェクトルートに `.markdownlint.json` を置く。JSON形式を推奨し、VS Code拡張が自動的に読み取るため、拡張側の追加設定は不要（6.2.1）。

```json
{
  "default": true,
  "MD013": false,
  "MD024": { "siblings_only": true },
  "MD033": {
    "allowed_elements": ["br", "details", "summary", "img"]
  }
}
```

- `"default": true`：全ルールを有効にする。
- `false`：個別ルールを無効化する。
- オブジェクト：ルールのオプションを変更する。

### 本文が具体名を挙げるルール

| ルール | デフォルト時の挙動 | 本書の推奨調整 | 理由 |
|---|---|---|---|
| `MD013` | 1行が80文字を超えると「行が長すぎる」と警告 | `false` で無効化 | 日本語文の途中でソフト改行すると、レンダリング時に半角スペースが入って不自然になるため |
| `MD024` | ファイル内の重複見出しをすべて警告 | `{ "siblings_only": true }` | 章ごとの「まとめ」「参考リンク」等は自然に重複するため。同じ階層の兄弟見出しだけを検査する |
| `MD033` | HTMLタグを検出して警告 | 必要なタグを `allowed_elements` に追加 | `<details>` 等、Markdownだけで表せない要素を許可するため。例では `br`、`details`、`summary`、`img` |

本文中でルール名と動作が具体的に説明されているのは、この3つである。他の推奨事項と個別のmarkdownlintルール名との対応は本文では明示されていない（6.2.2）。

### 保存時の自動修正

VS Codeの `settings.json` に次を設定する（6.2.3）。

```json
{
  "editor.codeActionsOnSave": {
    "source.fixAll.markdownlint": "explicit"
  }
}
```

- `"explicit"` は手動保存時だけ実行し、自動保存では実行しない。
- 末尾空白の削除や空行追加など、安全な修正だけが対象。
- 内容を変える修正は行わない。
- 設定しなくても、拡張を導入すれば警告表示は有効。

### チーム開発

- `.markdownlint.json` をGitリポジトリへコミットし、全員に同じルールを適用する。
- 口頭の書式ルール共有とレビュー負担を減らす。
- コマンドライン版 `markdownlint-cli2` をGitHub Actions等に組み込み、プルリクエスト時に自動検査できる（6.2.4）。
- 議事録テンプレート等と設定ファイルを一緒にリポジトリへ置けば、フォーマットと検査ルールを同時に統一できる（6.4）。

## 5. Mermaid

### 扱える図の種類

| 図の種類 | 用途 |
|---|---|
| `flowchart` | 処理の流れ、条件分岐 |
| `sequenceDiagram` | システム間のメッセージのやり取り |
| `gantt` | プロジェクトのスケジュール |
| `erDiagram` | データベースのテーブル間の関連 |
| `classDiagram` | クラスの構造と関連 |
| `stateDiagram-v2` | 状態の変化と遷移条件 |
| `pie` | 割合の可視化 |
| `journey` | ユーザー体験の流れと満足度 |
| `mindmap` | アイデアの階層構造 |
| `gitgraph` | ブランチとコミットの履歴 |

出典：8.5.1。本文ではフローチャート、シーケンス図、ER図を詳しく扱い、8.5.4でガントチャート、パイチャート、状態遷移図の例を示す。

### 推奨する書き方

- フェンスドコードブロックの言語名を `mermaid` にし、1行目に図の種類を書く（8.5.2）。
- IDは半角英数字で付け、表示テキストは括弧や `as` で分離する（8.5.2、8.5.7）。
- `A`、`B` より `login`、`validate` のような意味のあるIDを使う（8.5.5）。
- 宣言行の次から4スペースでインデントする（8.5.5）。
- ノードが10を超えるなら図を分割するか、他ツールで作成した画像にする（8.5.5）。
- フローチャートの方向は上から下または左から右を基本とし、下から上・右から左は非推奨（8.5.3）。
- 非対応プラットフォームでは画像へ変換して埋め込む（8.5.8）。
