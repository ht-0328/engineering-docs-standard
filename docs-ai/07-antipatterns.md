# 07 アンチパターン集

**この章は、実際に見かける書き方と、その直し方を並べる。**

各項目は「悪い例 → 何が起きるか → 直し方 → 根拠の規則」の順に並べている。

## 使い方

**上から読む必要はない。** 手元の文書に当てはまるものを探す。

| 症状 | 見る項目 |
|---|---|
| AIが「文書に書いていない」と答える | 1、2、3 |
| AIが違うものの値を答える | 4、5、6 |
| AIが指示を守らない | 7、8、9、10 |
| AIが道具を呼ばない、または呼びすぎる | 11、12 |

---

## 1. 主語を前の節に置く

**節が切り分けられると、何についての話か分からなくなる。**

### 悪い例

```markdown
## 概要

Haiton には夜間集計ジョブがある。

## 保持

上記のジョブが出力するものは、90日間保持される。
```

### 何が起きるか

「保持」の節だけが切り出されて渡ると、**何が90日間保持されるのか決まらない。**

実験では、この書き方の文書に対して、あるモデルは8問すべてで「わからない」と答えた。別のモデルは、誤った節を渡されると5/8で**別のジョブの値を断定して答えた。**

### 直し方

```markdown
## Haiton 夜間集計ジョブのログ保持期間

Haiton の夜間集計ジョブのログは、90日間保持する。
```

**規則**: `AD-01`、`AD-03`

## 2. 見出しを一般名にする

**断片になったとき、その節が何の話か示すものが無くなる。**

### 悪い例

```markdown
## 概要
## 設定
## 注意
## 補足
```

### 何が起きるか

**断片になった瞬間、その節が何の話か分からなくなる。** さらに、関係のない検索でも拾われる。

書籍は、名前が大雑把だと「不要な場面でもモデルがツールを呼び出してしまう」と述べている。**見出しにも同じことが起きる。**

### 直し方

```markdown
## Haiton 夜間集計ジョブを再実行できる条件
## Haiton 夜間集計ジョブのログ保持期間
```

**製品名・機能名・その節が答える問いの3つを入れる。**

**規則**: `AD-02`

## 3. 情報を図だけに置く

**AIは図の中の手順を使えない。**

### 悪い例

```markdown
## デプロイの手順

![デプロイの流れ](deploy-flow.png)
```

### 何が起きるか

**AIは図の中の手順を使えない。** 代替テキストを付けても、それは図の説明であって手順そのものではない。

### 直し方

```markdown
## Haiton をデプロイする手順

1. `make verify` を実行し、終了コードが 0 であることを確認する。
2. `make deploy-staging` を実行する。
3. 検証環境で `/health` が `200` を返すことを確認する。
4. `make deploy-prod` を実行する。

![Haiton のデプロイの流れ。検証、検証環境への配置、確認、本番への配置の4段階](deploy-flow.png)
```

**本文を先に、図を後に置く。** 人は図で分かれば本文を飛ばせる。AIは本文を読む。

**規則**: `AD-09`、`AH-02`

## 4. 廃止した手順を同じ文書に残す

**AIは古いほうを答えとして拾うことがある。**

### 悪い例

```markdown
## デプロイの手順

`make deploy` を実行する。

## 旧デプロイ手順

`./scripts/deploy.sh --legacy` を実行する。
```

### 何が起きるか

**AIは古いほうを拾うことがある。** 実測レポートは、誤答の中身が「まぎらわしい記述そのもの」であることが多いと報告している。

査読つきの研究も、関係のない記述を混ぜると成績が劇的に下がることを示している。

### 直し方

**消す。** 履歴はGitにある。

残す必要があるなら、別のファイルに移す。同じ文書に残さざるを得ないなら、末尾にまとめ、見出しで廃止と明示する。

```markdown
## 廃止した手順（2026-03-01 に使用を停止した。実行しない）
```

**規則**: `AD-06`

## 5. 同じものを違う語で書く

**どの語で検索されても、他の記述に当たらなくなる。**

### 悪い例

```markdown
夜間のジョブが失敗した場合は再実行する。
このバッチ処理は最大3回まで実行できる。
当該タスクの状態は管理画面で確認する。
```

「ジョブ」「バッチ処理」「タスク」が同じものを指している。

### 何が起きるか

**そのどれで検索されても、他の記述に当たらない。** 査読つきの研究は、語がそのまま一致しないと長い文脈で見つけられなくなることを示している。

### 直し方

**一つに決める。利用者が実際に使う語を選ぶ。**

```markdown
Haiton 夜間集計ジョブが失敗した場合は再実行する。
Haiton 夜間集計ジョブは最大3回まで再実行できる。
Haiton 夜間集計ジョブの状態は管理画面で確認する。
```

**繰り返しを恐れない。** 節をまたぐ繰り返しは、人にはほとんど気にならない。

**規則**: `AD-05`、`AH-01`

## 6. 誤りの文言を要約して書く

**利用者が貼り付けた文言と一致せず、見つからない。**

### 悪い例

```markdown
件数が上限を超えるとエラーになる。上限の設定を確認する。
```

### 何が起きるか

利用者は画面に出た文言をそのまま貼って質問する。**その文字列が文書に無ければ一致しない。**

### 直し方

```markdown
## Haiton 夜間集計ジョブが `E-4012 batch size exceeded` で失敗したときの対処

`E-4012 batch size exceeded` は、処理件数が 50000件 を超えたときに出る。
```

**規則**: `AD-07`

## 7. 曖昧な語で指示する

**守ったかどうかを、あとから確かめられない。**

### 悪い例

<!-- doclint-disable vague_words -->

```markdown
- コードは適切にフォーマットする
- 必要に応じてテストを追加する
- 可能な限り依存を減らす
```

<!-- doclint-enable -->

### 何が起きるか

**守ったかどうかを、あとから確かめられない。** そのため、守られたかも分からない。

### 直し方

```markdown
- インデントは空白2つにする
- 追加した関数には、正常系と異常系のテストを1件ずつ書く
- 新しい依存を足すときは、その理由を変更提案に書く
```

**判定の基準は「守ったかどうかを機械的に確かめられるか」である。**

**規則**: `AN-05`

## 8. 指示書に一般知識を書く

**毎回読まれ、毎回トークンを食い、何も伝えていない。**

### 悪い例

```markdown
## テストについて

テストとは、コードが期待どおり動くことを確認する作業です。
テストには単体テスト、結合テスト、E2Eテストがあります。
単体テストは関数単位で、結合テストは複数の部品を組み合わせて……
```

### 何が起きるか

**毎回読まれ、毎回トークンを食う。そして何も伝えていない。** AIはテストが何かを知っている。

公式文書は、この形を悪い例として名指ししている。

### 直し方

```markdown
## テスト

- 単体テストは `tests/unit/` に置く
- `make test` は単体テストだけを走らせる。結合テストは `make test-integration`
- **外部APIを叩くテストは書かない。** `tests/fixtures/` の応答を使う
```

**その組織・そのプロジェクトに固有のことだけを書く。**

**規則**: `AN-09`

## 9. 矛盾した指示を残す

**AIは質問してこない。黙ってどちらかを選ぶ。**

### 悪い例

同じ指示書の中に、離れて置かれている。

```markdown
（冒頭）
コミットは日本語で書く。

（末尾）
コミットメッセージは Conventional Commits に従い、英語で書く。
```

### 何が起きるか

**AIはどちらかを黙って選ぶ。** 質問してこない。

> "if two rules contradict each other, Claude may pick one arbitrarily."

### 直し方

**片方を消す。** 読み直す時機は `AN-06` に書いてある。**指示書に1項目足すたびに、そのファイル全体を読み直す。**

| 生まれやすい場所 |
|---|
| 階層の違う指示書のあいだ |
| 同じファイルの離れた場所 |
| 使わなくなった道具の手順 |

**規則**: `AN-06`

## 10. 指示書で強制しようとする

**強調しても、守られる保証は無い。**

### 悪い例

```markdown
**絶対に** `main` ブランチに直接コミットしないこと。
**必ず** コミット前に `make lint` を実行すること。
```

### 何が起きるか

**強調しても守られる保証は無い。** 公式文書はこう書いている。

> "Claude treats them as context, not enforced configuration."

### 直し方

**仕組みで止める。**

| 目的 | 使うもの |
|---|---|
| `main` への直接コミットを止める | ブランチ保護、または権限の設定 |
| コミット前に必ず `make lint` を走らせる | コミット前に割り込む仕組み（hook） |

**指示書には、仕組みで表せない方針だけを残す。**

**規則**: `AN-11`

## 11. 道具の説明文に「いつ使うか」を書かない

**呼ばれるべきときに呼ばれず、呼ばれるべきでないときに呼ばれる。**

### 悪い例

```yaml
name: search
description: 検索します
```

### 何が起きるか

2つ起きる。

1. **呼ばれるべきときに呼ばれない。** 何を検索するのか分からないため。
2. **呼ばれるべきでないときに呼ばれる。** 名前が一般的すぎるため。

書籍は「名前が大雑把だと不要な場面でもモデルがツールを呼び出してしまう」と述べている。

### 直し方

```yaml
name: search-haiton-runbooks
description: Haiton の運用手順書を全文検索し、該当する手順の見出しと本文を返す。
  Haiton のジョブ、デプロイ、障害対応について問われたときに使う。
  ソースコードの検索には使わない。
```

**「何をするか」と「いつ使うか」、そして「いつ使わないか」を書く。**

**規則**: `AK-01`、`AK-02`

## 12. 似た説明文の道具を並べる

**選択を誤る。**

### 悪い例

```yaml
- name: get_user
  description: ユーザーの情報を取得します
- name: fetch_user
  description: ユーザーのデータを取得します
- name: load_user_data
  description: ユーザー情報を読み込みます
```

### 何が起きるか

**選択を誤る。** 書籍はこう述べている。

> 「複数のツールで似たような説明を使うと、混乱と性能低下を招く。」

これは、まぎらわしい記述が正答率を下げるという実測と同じ形をしている。**道具の集合の中でも起きる。**

### 直し方

**まとめる。** 3つが同じことをしているなら1つにする。違うなら、違いが説明文から分かるようにする。

```yaml
- name: get_user_profile
  description: ユーザーIDから、表示名とメールアドレスを返す。認証には使わない。
- name: get_user_permissions
  description: ユーザーIDから、そのユーザーが持つ権限の一覧を返す。
```

**規則**: `AK-02`、`AK-03`

## 直したあとに確かめること

**直したら測る。** 直したつもりで直っていないことがある。

1. **その節だけを切り取って、人に見せる。** 答えられるか。
2. **誤った節をわざと渡して、AIに聞く。** 「わからない」と答えるか、それとも別の値を答えるか。
3. **使う予定のモデルすべてで試す。** モデルによって失敗の仕方が違う。

手順は [付録 実験の記録](appendix-experiments.md) にある。
