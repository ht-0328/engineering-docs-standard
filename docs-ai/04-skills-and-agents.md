# 04 スキルと道具の規則

**この章の規則は、AIだけが読む文書に当てはめる。** スキル定義、エージェント定義、道具（ツール）の説明文が対象である。

規則IDは `AK-xx` を使う。

## この章の根拠は弱い

**先に断っておく。** この章の根拠は、大半がベンダーの公式文書である。査読つきの研究は無く、実測も示されていない。

そのため、この別冊の基準に従って数え直した。**ベンダー文書（Anthropic と OpenAI）は、合わせて2出典分までとして数える。** 3出典目には、公開仕様（MCP）、書籍、または自分で測った結果が要る。

| 規則 | 中核の基準を満たすか | 規範度 |
|---|---|---|
| `AK-02` 名前を具体的にする | **満たす**（書籍、MCP、実測） | 必須 |
| `AK-03` 道具の数を絞る | **満たす**（`AD-11` の根拠を共有する） | 必須 |
| `AK-04` 後から読み込ませる | **満たす**（書籍、llms.txt、MCP） | 必須 |
| `AK-01` 何をするか・いつ使うか | **満たさない。** 根拠はベンダー文書2件だけである | **必須**（下に理由） |
| その他8件 | 満たさない | 推奨か任意 |

**`AK-01` だけは、根拠が薄いのに必須にしている。** これを守らないと道具が呼ばれず、機能そのものが動かないためである。**出典数と規範度は別の軸である。**

数え直しの経緯は [research/cross-reference-ai.md](../research/cross-reference-ai.md) にある。

## 説明文は、選ばれるための文である

**この章の前提である。**

道具の説明文は、機能の説明ではない。**AIがその道具を選ぶかどうかを決める文**である。

MCP の仕組みでは、次の順に進む。

1. 道具の一覧（名前、説明文、引数の定義）を取得する。
2. それをモデルに渡す。
3. **モデルは利用者の意図と各説明文を照らし合わせ、道具を選ぶ。**

スキルも同じである。起動時には名前と説明文だけが読まれ、そこで「関係あるか」が判断される。

**説明文は、選択を決める主要な材料の一つである。** 名前と引数の定義も使われる。**説明文が不明確だと、選ばれにくくなる。**

## AK-01 選択のときに読まれる場所に「何をするか」と「いつ使うか」を書く

**必須。ただし根拠はベンダー文書2件だけである。**

**中核の基準（独立3出典以上）を満たしていない。** それでも必須にしているのは、守らないと道具が呼ばれず、機能そのものが動かないためである。

**書く場所は道具によって違う。**

| 道具 | 「いつ使うか」を書く場所 |
|---|---|
| スキル（Anthropic） | `description` の中。**そこだけが常に読まれる** |
| 関数定義（OpenAI） | **システムプロンプト。** `description` には目的と引数を書く |

**規則が求めるのは「説明文に書くこと」ではなく、「選択のときに読まれる場所に書くこと」である。**

公式が挙げる良い例である。

```yaml
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
```

前半が「何をするか」、`Use when` 以降が「いつ使うか」である。

悪い例として挙がっているもの。

```yaml
description: Helps with documents
description: Processes data
description: Does stuff with files
```

**共通するのは、対象と場面が特定できないことである。**

### 「いつ使うか」をどこに書くかは、道具によって違う

**2社で指針が食い違う。両論を書く。**

| 出典 | 立場 |
|---|---|
| Anthropic（スキル） | **説明文の中に書く。** 両方を入れることを必須としている |
| OpenAI | **システムプロンプトに書く。** 説明文には目的と引数を書く |

> "Use the system prompt to describe when (and when not) to use each function."

**どちらが正しいかではない。仕組みが違う。**

Anthropic のスキルは、説明文だけが常に読まれる。だから選択の手がかりをそこに置くしかない。OpenAI の関数定義は、システムメッセージに一括で入る。だから分けられる。

**判定の仕方**: その説明文が、選択のときに読まれるかを確かめる。読まれるなら、そこに「いつ使うか」を書く。

**出典**: `SRC-AIEXT-003`、`SRC-AIEXT-009`

## AK-02 名前を具体的にする。一般的な名前を避ける

**必須。3者（Anthropic、OpenAI、MCP 仕様）が一致している。**

| 出典 | 述べていること |
|---|---|
| Anthropic | `helper`、`utils`、`tools`、`documents`、`data`、`files` を避ける。動名詞（`processing-pdfs`）を勧める |
| OpenAI | 自明で直感的な名前にする（最小驚きの原則） |
| MCP | `search` のような名前は他のサーバーとぶつかる。サーバー名を前に付ける |

**「何にでも当てはまる名前」は、何にも当たらない。**

形式上の制約も道具ごとにある。

| 対象 | 名前の制約 |
|---|---|
| スキル（Anthropic） | 64文字以内。英小文字・数字・ハイフンのみ。`anthropic` と `claude` は使えない |
| MCP の道具 | 1〜128文字。英数字と `_` `-` `.` のみ |

**出典**: `SRC-AI-002`（4.1.1「スコープを絞った正確な名前を付ける」）、`SRC-AIEXT-003`、`SRC-AIEXT-009`（MCP の命名規則）、`SRC-AIEXP-001`（見出しを具体的にすると検索が当たる）

## AK-03 道具の数を絞る

**必須。** ただし根拠の強さは項目によって違う。

**対象は「作業の開始時にモデルへ渡す道具の定義」である。** 使える道具の総数ではない。

| 出典 | 述べていること | 強さ |
|---|---|---|
| Anthropic | 膨らんだ道具の集合は判断を曖昧にする。最小限で用の足りる集合にする | 指針 |
| OpenAI | ターンの開始時点で使える関数は20個未満を目指す | **「緩い提案」と本人が断っている** |

**MCP の命名衝突は、この規則ではなく `AK-02`（名前を具体的にする）の根拠である。**

**合否の基準は置かない。** 20個という数値も提案にとどまる。**判断はこうする。**

| 確かめること |
|---|
| 開始時に渡している道具のうち、**直近10回の作業で一度も呼ばれなかったものはどれか** |
| それらを、必要になってから読み込ませる形に移せるか |

説明文はトークンを食い、課金される。OpenAI は明記している。

> "callable function definitions count against the model's context limit and are billed as input tokens."

**開始時にモデルへ渡す定義を増やすと、そのぶん入力トークンを消費し、課金される。**

**出典**: `SRC-AI-001`（6.1。簡潔さの理由は効果・費用・速度）、`SRC-AI-003`（3.2.2）、`SRC-AIEXT-005`、`SRC-AIEXT-008`（A-2）、`SRC-AIEXT-009`（20個未満）。**渡す量を絞るという原則そのもの**（`AD-11`）と根拠を共有する。

## AK-04 使わないものは、後から読み込ませる

**必須。3者（Anthropic、OpenAI、MCP 仕様）が一致している。**

呼び名は違うが、同じ考え方である。

| 出典 | 呼び名 |
|---|---|
| Anthropic（スキル） | 段階的な開示 |
| OpenAI | tool search |
| MCP | 動的な取得 |

スキルの読み込みは3段階になっている。

| 段階 | 読まれるもの | いつ |
|---|---|---|
| 1 | 名前と説明文 | 常に |
| 2 | 本体 | 関係すると判断されたとき |
| 3 | 参照先のファイル | 必要になったとき |

**段階3に置いたものは、読まれるまで費用がかからない。** 大きな資料や例は、そこに置く。

本体は500行以内が目安とされている。**この数値に測定の裏づけは示されていない。**

**出典**: `SRC-AI-001`（6.5.2。削るときは重要度の下位層から）、`SRC-AIEXT-001`（`Optional` 節）、`SRC-AIEXT-002`、`SRC-AIEXT-003`、`SRC-AIEXT-009`

## AK-05 新人が読んで使えるかで判定する

**推奨。**

> "Can an intern/human correctly use the function given nothing but what you gave the model? (If not, what questions do they ask you? Add the answers to the prompt.)"

**手順は3つである。**

1. AIに渡す情報だけを、その仕事を知らない人に見せる。
2. 正しく使えるかを見る。
3. 使えないなら、その人が聞いてくる質問を書き出す。**そのうち、この道具に固有の質問への答えだけを説明文に足す。**

**一般知識についての質問には答えを書かない。** 説明文はトークンを食い、課金される（`AK-03`）。

**この試験に合格の基準を置く。** 次の3つを満たせば合格とする。

| 確かめること |
|---|
| その人が、道具を呼ぶべき場面を正しく選べる |
| 引数に何を入れるかを、渡した情報だけで決められる |
| 呼ぶべきでない場面を1つ挙げられる |

**人に見せる手間はかかるが、AIの挙動を見るより原因が特定しやすいことがある。** ただし、これを比べた測定はしていない。

**出典**: `SRC-AIEXT-009`

## AK-06 説明文は三人称で書く

**推奨。1社しか述べていない。**

> "**Always write in third person**. The description is injected into the system prompt, and inconsistent point-of-view can cause discovery problems."

| 判定 | 例 |
|---|---|
| 良い | Excelファイルを処理し、報告書を作る |
| 避ける | 私がExcelファイルの処理を手伝います |
| 避ける | あなたはこれを使ってExcelファイルを処理できます |

理由は、説明文がシステムプロンプトに埋め込まれるためである。**視点が混ざると主体が曖昧になり、選ばれ方を妨げることがある。** 原文も `can cause` であり、必ず起きるとは述べていない。

**Anthropic だけが述べている。** OpenAI と MCP にはこの指定が無い。そのため推奨にとどめる。

**出典**: `SRC-AIEXT-003`

## AK-07 参照は1段階までにする

**推奨。1社しか述べていない。**

> "Keep references one level deep from SKILL.md"

理由が示されている。参照の参照になると、AIはファイルの先頭だけを見て済ませることがあり、情報が欠ける。

```text
良い形
  SKILL.md → reference.md
  SKILL.md → examples.md

避ける形
  SKILL.md → advanced.md → details.md
```

**出典**: `SRC-AIEXT-003`

## AK-08 100行を超える参照先には目次を置く

**推奨。1社しか述べていない。**

> "For reference files longer than 100 lines, include a table of contents at the top."

理由は `AK-07` と同じである。**先頭しか読まれないことがあるため、先頭に全体像を置く。**

**出典**: `SRC-AIEXT-003`

## AK-09 無効な状態を表現できない形にする

**推奨。**

OpenAI が挙げる悪い例は `toggle_light(on: bool, off: bool)` である。`on` と `off` を両方 `true` にできてしまう。

**引数の設計で防げる誤りを、説明文で防ごうとしない。** 列挙型や構造を使い、**そもそも間違った呼び方ができないようにする。**

**これは文書の規則ではなく設計の規則である。** しかし、説明文を書く前に効く。

**出典**: `SRC-AIEXT-009`

## AK-10 すでに分かっていることを書かせない

**推奨。**

> "Don't make the model fill arguments you already know."

前の文脈で値が決まっているなら、その引数を無くし、呼び出す側のコードで埋める。

**続けて呼ばれる道具をまとめるかは、条件による。**

| まとめてよい | 分けておく |
|---|---|
| 途中で止める必要がない | 途中の結果を見て次を決める |
| 権限が同じ | 権限が違う |
| 失敗したときの扱いが同じ | 片方だけやり直したい |

**出典が述べているのは「すでに分かっている引数を埋めさせない」ことだけである。** 道具をまとめることまでは述べていない。**この表はこの別冊が運用上決めたものである。**

**出典**: `SRC-AIEXT-009`

## AK-11 評価を先に作り、測ってから書く

**推奨。**

> "**Create evaluations BEFORE writing extensive documentation.**"

順序が定められている。

1. スキル無しで代表的な作業をやらせ、失敗を記録する。
2. その失敗を突く評価を3件作る。
3. スキル無しの成績を測る。これが基準値になる。
4. 評価を通る**最小限の**指示だけを書く。
5. 実行し、基準値と比べ、直す。

**「書いてから測る」ではなく「測ってから書く」である。**

理由も書かれている。

> "This approach ensures you're solving actual problems rather than anticipating requirements that may never materialize."

**この別冊の実験も、この順序に従っている。**

### 使う予定のモデルすべてで試す

> "What works perfectly for Opus might need more detail for Haiku."

**モデルが違えば、必要な説明の量が変わる。**

**出典**: `SRC-AIEXT-003`

## AK-12 手順には確認欄を付け、検証の輪を作る

**任意。1社しか述べておらず、測定も無い。**

複雑な作業では、AIが写して進捗を印けるチェックリストを与えることが勧められている。

```markdown
- [ ] 手順1: すべての出典を読む
- [ ] 手順2: 主要な主張を並べる
- [ ] 手順3: 出典と突き合わせる
```

理由は「明確な手順が、重要な検証を飛ばすことを防ぐ」である。

検証の輪は「検証する → 誤りを直す → もう一度検証する」の繰り返しである。**検証器はプログラムでなくてもよい。** 文書（スタイルガイド）を検証器として使う例も挙がっている。

**出典**: `SRC-AIEXT-003`

## 例を入れるかどうかは、モデルによる

**2社の指針が食い違う点である。**

| 出典 | 立場 |
|---|---|
| Anthropic | 例を入れる。「例は説明よりも明確に伝わる」 |
| OpenAI | 入れてよい。**ただし推論するモデルでは性能を損なうことがある** |

> "Adding examples may hurt performance for reasoning models."

**どちらも測定結果を示していない。**

この別冊は、次の扱いにする。

1. 例を入れるかは、**使うモデルで試して決める**（`AK-11`）。
2. 入れるなら、入力と出力の対にする。抽象的な説明を例と呼ばない。
3. **推論するモデルを使う場合は、例を外した版も測る。**
