# 03 AIへの指示書の規則

**この章の規則は、AIに仕事をさせるための文書に当てはめる。**

**規則によって対象が違う。**

| 規則 | 対象 |
|---|---|
| `AN-01` から `AN-04` | **リポジトリに置く指示書だけ**（`CLAUDE.md`、`AGENTS.md`、経路を限った規則）。名前・置き場所・行数を扱うため |
| `AN-05` から `AN-12` | 上に加えて、**システムプロンプトと作業の依頼文**にも当てはまる |

規則IDは `AN-xx` を使う。

## 指示書と、AIが読む文書は別物である

[02章](02-ai-readable-docs.md) が扱うのは、**AIが必要なときに探して読む文書**である。この章が扱うのは、**AIが常に読む文書**である。

| 観点 | AIが読む文書（`AD-xx`） | AIへの指示書（`AN-xx`） |
|---|---|---|
| いつ読まれるか | 探されたときだけ | **作業の開始時に、探さずに読まれる** |
| 量が増えると | 検索の精度が落ちる | **その範囲のすべての作業で精度が落ちる** |
| 主な失敗 | 見つからない | **守られない** |

**指示書は、書けば書くほど守られなくなる。** これが人向けの文書との最大の違いである。

### 指示書にも、常に読まれるものとそうでないものがある

**「毎回読まれる」のは、適用範囲の中でのことである。**

| 種類 | いつ読まれるか |
|---|---|
| リポジトリの根に置いた指示書 | そのリポジトリでの作業なら毎回 |
| サブディレクトリに置いた指示書 | **そのディレクトリのファイルを触るときだけ** |
| 経路を指定した規則 | **一致するファイルを触るときだけ** |

**この違いを使って量を減らすのが `AN-03` と `AN-08` である。**

## AN-01 指示書を、人向けの README と分ける

**必須。**

公開仕様 AGENTS.md は、住み分けを明文にしている。

> "README.md files are for humans: quick starts, project descriptions, and contribution guidelines"
> （README.md は人のためのものである。手早い始め方、プロジェクトの説明、貢献の手引き）

AGENTS.md が持つのは次である。

> "the extra, sometimes detailed context coding agents need."

**常に読み込ませる指示書に、人向けの説明を重ねない。** 量が増えるほど遵守が落ちるためである。**人にも要る情報（組み立てや試験の手順）は、READMEから参照できる形にしてよい。**

| 書くもの | 置き場所 |
|---|---|
| これは何か。誰のためか。どう始めるか | README.md |
| 組み立てと試験の命令。守る決まり。落とし穴 | 指示書 |

**出典**: `SRC-AIEXT-004`

## AN-02 決まった名前で、決まった場所に置く

**必須。**

指示書の価値は中身だけではない。**「そこを見れば必ずある」という約束**にある。AGENTS.md はこれを "a dedicated, predictable place" と呼んでいる。

道具によって読むファイル名が違う。ここは実測ではなく仕様の問題なので、公式文書に従う。

| 道具 | 読むファイル |
|---|---|
| AGENTS.md に対応する道具（20種以上） | `AGENTS.md` |
| Claude Code | `CLAUDE.md`。**`AGENTS.md` は読まない** |

**この点は、二次情報が誤っていた。** 「Claude Code は `AGENTS.md` を代わりに読む」と書いた解説記事が複数あったが、公式文書は明確に否定している。

> "Claude Code reads `CLAUDE.md`, not `AGENTS.md`."

両方の道具を使う場合、公式が示す対処は、`CLAUDE.md` から取り込むことである。

```markdown
@AGENTS.md

## Claude Code だけに向けた指示

`src/billing/` の変更では計画モードを使う。
```

**出典**: `SRC-AIEXT-004`、`SRC-AIEXT-007`

## AN-03 適用範囲を、置き場所で表す

**必須。**

「フロントエンドの場合は」「テストを書くときは」と本文で場合分けすると、その条件は毎回読まれる。**関係ない作業のときも読まれる。**

置き場所で表せば、関係するときだけ読まれる。

| 適用範囲 | 置き場所 |
|---|---|
| 組織全体 | 組織向けの場所（道具ごとに決まっている） |
| 個人の好み | 利用者向けの場所 |
| プロジェクト全体 | リポジトリの根 |
| 特定のディレクトリだけ | そのディレクトリ |
| 特定のファイル種別だけ | 経路を指定できる規則のファイル |

AGENTS.md の仕様は、近いものが優先されると定めている。

> "Agents automatically read the nearest file in the directory tree, so the closest one takes precedence."

**出典**: `SRC-AIEXT-004`、`SRC-AIEXT-007`

## AN-04 CLAUDE.md は200行未満を目標にする

**推奨。**

**この数値は `CLAUDE.md` に固有である。** 他の指示書へそのまま当てはめない。`AGENTS.md` の公開仕様は、長さの上限を定めていない。

公式文書が数値を示している。

> "target under 200 lines per CLAUDE.md file"
> （`CLAUDE.md` 1ファイルあたり200行**未満**を目標にする）

**原文は `under 200`、つまり200行を含まない。**

理由も書かれている。

> "Longer files consume more context and reduce adherence."
> （長いファイルは文脈をより多く消費し、指示の遵守を下げる）

**注意が2つある。**

1. **この数値に測定結果は示されていない。** 公式の推奨であって、実験の結果ではない。
2. **これは1つの製品の推奨である。** 他の道具では違う値になりうる。

**200行に達したら、削るか、範囲を限った場所へ移す。** ファイルを分けても、取り込み（`@`）で読み込むなら読み込み量は減らない。公式文書もそう書いている。

> "Splitting into `@path` imports helps organization but doesn't reduce context"

**出典**: `SRC-AIEXT-007`。加えて、**渡す量を絞るという原則そのもの**（`AD-11`）の根拠を共有する。`AD-11` は、ベンダー以外の6出典（書籍2冊、llms.txt、Chroma の実測、査読つき研究、MCP 仕様）が直接支持している。

## AN-05 確かめられる形で書く

**必須。**

公式文書が挙げる対比である。

| 良い | 悪い |
|---|---|
| Use 2-space indentation | Format code properly |
| Run `npm test` before committing | Test your changes |
| API handlers live in `src/api/handlers/` | Keep files organized |

**判定の方法は「指示の中身が一意に決まるか」である。**

**「あとから確かめられるか」とは別の話である。** 上の `npm test` の例は、指示としては一意だが、**実行したかどうかを後から確かめる手段は指示書には無い。** 確実に実行させたいなら、仕組みで行う（`AN-11`）。

日本語でも同じである。

<!-- doclint-disable vague_words -->

| 良い | 悪い |
|---|---|
| インデントは空白2つにする | 適切にインデントする |
| コミット前に `npm test` を実行する | 必要に応じてテストする |
| APIの処理は `src/api/handlers/` に置く | ファイルをきちんと整理する |

<!-- doclint-enable -->

本編の S-07（曖昧な語を数値・固有名詞・日時に置き換える）と同じ規則である。

### 新人の試験

OpenAI の公式ガイドは、判定の仕方を一つ示している。

> "Can an intern/human correctly use the function given nothing but what you gave the model? (If not, what questions do they ask you? Add the answers to the prompt.)"

**渡した情報だけで、新人が正しくできるかを見る。** できないなら、その人が聞いてくる質問を考える。

**書き足すのは、プロジェクト固有・作業固有の質問への答えだけである。** 一般知識についての質問には答えを書かない（`AN-09`）。書き足すと、そのぶん毎回読まれる量が増える。

**この試験は、指示書にも文書にも使える。** ただし書き足す範囲は上のとおり限る。

**出典**: `SRC-AIEXT-007`、`SRC-AIEXT-009`

## AN-06 矛盾を残さない

**必須。**

> "if two rules contradict each other, Claude may pick one arbitrarily."
> （2つの規則が矛盾していると、Claudeはどちらかを恣意的に選ぶ**ことがある**）

**矛盾は誤りとして報告されるとは限らない。** 人が読む文書なら、たいてい質問が返ってくる。AI相手では、**質問されないまま一方が選ばれることがある。**

**優先順位が決まっている食い違いは、矛盾ではない。**

`AN-03` のとおり、近いところに置いた指示書が優先される。**それは意図した上書きである。**

問題になるのは、**どちらが勝つか決まっていない食い違い**である。

| 生まれる場所 | 例 |
|---|---|
| **同じファイルの離れた場所** | 冒頭の方針と、末尾の例外 |
| **同じ階層の別のファイル** | `AGENTS.md` と `.claude/rules/` の規則 |
| 古い決まりを消し忘れる | 使わなくなった道具の手順が残る |

**読み直す時機を決めておく。**

| 時機 | 何をするか |
|---|---|
| 指示書に1項目足すとき | **そのファイル全体を読み直す** |
| 使っていた道具をやめたとき | その道具に関する記述を消す |
| 本編の O-02（定期確認）で開いたとき | そのとき合わせる |

**「定期的に」とだけ書くと、いつやるか決まらない。** 上のように、**起きたことに結び付ける。**

消すことは、書くことと同じだけ重要である。

**出典**: `SRC-AIEXT-007`

## AN-07 見出しと箇条書きで区切る

**推奨。**

公式文書は、AIも人と同じように走査すると述べている。

> "Claude scans structure the same way readers do: organized sections are easier to follow than dense paragraphs."

指示文の設計についても、役割ごとに節へ分けることが勧められている。背景、指示、道具の使い方、出力の形、といった区切りである。

**出典**: `SRC-AI-001`（6.1。導入部で先に焦点を絞ると出力が良くなる）、`SRC-AIEXT-007`、`SRC-AIEXT-002`、`SRC-AIEXT-008`（A-1。位置による効き方の違い）

## AN-08 常に要るものだけを、常に読まれる場所に置く

**必須。**

**この規則は `AN-04`（200行）より根本的である。** 行数を削るのではなく、置き場所を変える。

| その情報は | 置き場所 |
|---|---|
| 毎回の作業で要る | 指示書 |
| 特定の作業のときだけ要る | スキル（[04章](04-skills-and-agents.md)） |
| 特定のファイルを触るときだけ要る | 経路を限った規則 |
| **現状を見れば分かる** | **書かない** |

最後の行が効く。公式文書は、コードから読み取れることを指示書に書かないよう求めている。

**「守るべき決まり」と「いまの状態」は分ける。**

| 書く | 書かない |
|---|---|
| **これから置く場所の決まり**（APIの処理は `src/api/handlers/` に置く） | いまあるディレクトリの一覧 |
| 使うと決めた道具 | 依存ライブラリの一覧 |

`AN-05` の良い例が配置先を書いているのは、**それが守るべき決まりだからである。** 現状の列挙ではない。

**出典**: `SRC-AI-001`（6.5.2「重要度の階層」。削るときは下位層から）、`SRC-AIEXT-001`（`Optional` 節）、`SRC-AIEXT-007`、`SRC-AIEXT-003`、`SRC-AIEXT-009`

## AN-09 AIが既に知っていることを書かない

**必須。**

スキルの公式文書は、既定の前提をこう置いている。

> "Only add context Claude doesn't already have."

各記述について3つを問えとしている。

1. この説明は本当に必要か。
2. これは知っていると仮定してよいか。
3. この段落はトークンの代価に見合うか。

**2番目は、そのままでは確かめられない。** モデルによって知っていることが違うためである。**確かめられる形に置き換える。**

| 消してよい | 判定 |
|---|---|
| リポジトリの中を見れば分かること | `grep` や `ls` で取れるか |
| 公開された仕様や標準ライブラリに書いてあること | 一次情報のURLを示せるか |
| 言語や道具の一般的な使い方 | その道具の公式文書に書いてあるか |

**このどれかに当たるなら消す。** どれにも当たらないなら、その組織・そのプロジェクトに固有の情報である。**それは書く。**

**この置き換えに出典は無い。この別冊が運用上決めたものである。**

公式文書が挙げる悪い例は、「PDFとは何か」「ライブラリとは何か」を説明していた。**一般知識の説明が、名指しで悪い例になっている。**

**書くべきなのは、その組織・そのプロジェクトに固有のことだけである。**

**出典**: `SRC-AIEXT-003`

## AN-10 選択肢を並べず、既定を1つ示す

**推奨。**

> **Bad example: Too many choices** (confusing): "You can use pypdf, or pdfplumber, or PyMuPDF, or pdf2image, or..."

既定を1つ決め、**必要な例外だけを条件つきで書く。** 出典が否定しているのは選択肢を並べることであり、例外の数を1つに限れとは述べていない。

```markdown
テストは `pytest` で実行する。
非同期のテストだけは `pytest-asyncio` を使う。
```

**出典**: `SRC-AIEXT-003`、`SRC-AIEXT-009`

## AN-11 必ず守らせたいことは、文書ではなく仕組みで行う

**必須。この章で最も重要な規則である。**

公式文書は、指示書の限界をはっきり書いている。

> "Claude treats them as context, not enforced configuration."

> "there's no guarantee of strict compliance"

**指示書は「お願い」である。「設定」ではない。**

| 目的 | 使うもの |
|---|---|
| 特定の命令や経路を確実に止める | 権限の設定 |
| 決まった時点で必ず実行する | 実行前後に割り込む仕組み（hook） |
| 振る舞いの方針を示す | 指示書 |

**「指示書に書いたのに守られない」と悩む前に、それが指示書で扱うべきことかを見直す。**

**出典**: `SRC-AIEXT-007`

## AN-12 指示の細かさを、作業の壊れやすさに合わせる

**推奨。**

スキルの公式文書が示す考え方である。**細かく書けば良いのではない。**

**細かさは、次の2つで決める。どちらも確かめられる。**

| 問い | 確かめ方 |
|---|---|
| 失敗したとき、元に戻せるか | 戻す手順が書けるかどうか |
| 正解の手順が1通りに決まるか | 別のやり方でも同じ結果になるかどうか |

| 戻せるか | 手順は1通りか | 指示の細かさ | 書き方 | 例 |
|---|---|---|---|---|
| 戻せる | 複数ある | 粗く | 方針だけを文章で書く | コードレビューの観点 |
| 戻せる | 1通り | 中くらい | 雛形を示す | 報告書の書式 |
| **戻せない** | 1通り | 細かく | **実行する命令をそのまま書く** | データベースの移行 |

公式文書はこれを比喩で説明している。両側が崖の細い橋なら手すりを付ける。障害物のない野原なら方向だけ示す。

**細かく書きすぎると、想定していない状況で壊れる。** 粗く書きすぎると、壊れやすい作業で事故が起きる。

**出典**: `SRC-AIEXT-003`
