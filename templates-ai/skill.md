# SKILL.md の型

| 項目 | 内容 |
|---|---|
| 発信日 | （例: 2026-08-31） |
| 作成者 | （例: 山田 太郎（基盤チーム）） |
| 機密区分 | （例: 社内限） |
| 保守責任者 | （例: 基盤チーム） |
| 最終確認日 | （例: 2026-08-31） |
| 想定読者（宛先） | （例: スキルを作る開発者） |
| この文書を読んだあと読者ができること | （例: 呼ばれるスキルを書ける） |

## この型の使い方

**下の枠の中身を `SKILL.md` として置く。** この説明の部分は写さない。

守る規則は [docs-ai/04-skills-and-agents.md](../docs-ai/04-skills-and-agents.md) にある。

## 仕様として決まっていること

**守らないと動かない。**

| 項目 | 制約 |
|---|---|
| `name` | 64文字以内。英小文字・数字・ハイフンのみ。`anthropic` と `claude` は使えない |
| `description` | 空でないこと。1,024文字以内 |

## 型

````markdown
---
name: （例: verifying-haiton-runbooks）
description: （例: Haiton の運用手順書が docs-ai の規則を満たすか検査し、違反箇所と直し方を返す。手順書を書いたとき、レビューを頼まれたとき、「AIが読めるか」を問われたときに使う。ソースコードの検査には使わない。）
---

# （例: Haiton 運用手順書の検査）

## 使う場面

（例: `docs/runbooks/` の下のファイルを新しく書いたか、大きく直したとき。）

## 手順

写して、終わったものに印を付ける。

```
- [ ] 手順1: 対象のファイルを読む
- [ ] 手順2: 見出しごとに切り分けて確かめる
- [ ] 手順3: 違反を一覧にする
- [ ] 手順4: 直し方を添える
```

### 手順1 対象のファイルを読む

（例: 指定されたファイルを読む。指定が無ければ、`git diff` で変更されたものを対象にする。）

### 手順2 見出しごとに切り分けて確かめる

`##` の見出しごとに区切り、**その節だけを読んで意味が通るか**を見る。次を確かめる。

| 確かめること | 違反の例 |
|---|---|
| 主語があるか | （例: 「上記のジョブは」で始まっている） |
| 見出しに製品名と機能名があるか | （例: 「概要」「設定」） |
| 節をまたいで指す語が無いか | （例: 「これ」「前者」「同様に」） |

### 手順3 違反を一覧にする

行番号、違反した規則ID、該当箇所を並べる。

### 手順4 直し方を添える

**指摘だけを書かない。** 直した後の文をそのまま書く。

## 判定の基準

規則の全文は `reference/rules.md` にある。
（例: 違反が0件なら「合格」と書く。1件でもあれば「要修正」と書く。）
````

## 参照先のファイルを置くとき

| 規則 | 内容 |
|---|---|
| `AK-04` | 本体は500行以内を目安にする |
| `AK-07` | **参照は1段階まで。** 参照先からさらに参照しない |
| `AK-08` | 100行を超える参照先には、先頭に目次を置く |

```text
skill-name/
  SKILL.md          常に読まれるのは name と description だけ
  reference/
    rules.md        必要になったときだけ読まれる
    examples.md     必要になったときだけ読まれる
```

## 確かめること

- [ ] `description` に「何をするか」と「いつ使うか」の両方がある
- [ ] `description` に「いつ使わないか」がある
- [ ] `description` が三人称である（「私が」「あなたは」で始まっていない）
- [ ] 名前が具体的である（`helper`、`utils` のような名前でない）
- [ ] 本体が500行以内である
- [ ] 参照が1段階までである
- [ ] AIが既に知っていることを書いていない
- [ ] **使う予定のモデルすべてで試した**
