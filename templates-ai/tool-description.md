# 道具（ツール）の説明文の型

| 項目 | 内容 |
|---|---|
| 発信日 | （例: 2026-08-31） |
| 作成者 | （例: 山田 太郎（基盤チーム）） |
| 機密区分 | （例: 社内限） |
| 保守責任者 | （例: 基盤チーム） |
| 最終確認日 | （例: 2026-08-31） |
| 想定読者（宛先） | （例: MCP サーバーや関数呼び出しの道具を作る開発者） |
| この文書を読んだあと読者ができること | （例: 正しく選ばれる道具の説明文を書ける） |

## この型の使い方

**説明文は、機能の説明ではない。AIがその道具を選ぶかどうかを決める文である。**

守る規則は [docs-ai/04-skills-and-agents.md](../docs-ai/04-skills-and-agents.md) にある。

## 型

```json
{
  "name": "（例: search_haiton_runbooks）",
  "description": "（例: Haiton の運用手順書を全文検索し、一致した手順の見出しと本文を返す。Haiton のジョブ、デプロイ、障害対応について問われたときに使う。ソースコードの検索には使わない。設定値の取得にも使わない。）",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "（例: 検索する語。日本語でよい。手順書の本文と見出しを対象にする）"
      },
      "limit": {
        "type": "integer",
        "description": "（例: 返す件数。1から20まで。既定は5）"
      }
    },
    "required": ["query"]
  }
}
```

## 説明文の組み立て

**3つの文で書く。**

| 順 | 書くもの | 例 |
|---|---|---|
| 1 | **何をするか。** 何を受け取り、何を返すか | Haiton の運用手順書を全文検索し、一致した手順の見出しと本文を返す |
| 2 | **いつ使うか。** 引き金になる言葉を含める | Haiton のジョブ、デプロイ、障害対応について問われたときに使う |
| 3 | **いつ使わないか。** 似た道具との境界を書く | ソースコードの検索には使わない |

**3番目を書くと、選択の誤りが減る。** 書籍は「名前が大雑把だと不要な場面でもモデルがツールを呼び出してしまう」と述べている。

## 名前の付け方

| 判定 | 例 |
|---|---|
| 良い | `search_haiton_runbooks`、`get_user_permissions` |
| 悪い | `search`、`get`、`helper`、`run` |

**`search` のような名前は、他のサーバーの道具とぶつかる。** MCP の仕様は、サーバー名を前に付けて区別することを勧めている。

## 引数の設計

| 規則 | 内容 | 例 |
|---|---|---|
| `AK-09` | **無効な状態を表現できない形にする** | `toggle_light(on, off)` ではなく `set_light(state: "on" \| "off")` |
| `AK-10` | すでに分かっていることを書かせない | 直前の文脈で決まっている ID を引数にしない |
| — | **各引数に説明を付ける** | 形式（日付なら `YYYY-MM-DD`）と範囲を書く |

## 数を絞る

| 出典 | 目安 |
|---|---|
| OpenAI | ターンの開始時点で使える関数は20個未満を目指す（緩い提案と断っている） |
| Anthropic | 最小限で用の足りる集合にする |

**説明文はトークンを食い、課金される。** 使わない道具は、必要になってから読み込ませる。

## 確かめること

- [ ] 「何をするか」「いつ使うか」「いつ使わないか」の3つがある
- [ ] 名前が具体的である。他のサーバーとぶつからない
- [ ] **似た説明文の道具が他に無い**
- [ ] 各引数に、形式と範囲を書いた説明がある
- [ ] 無効な組み合わせを呼べない設計になっている
- [ ] **新人の試験を通る。** 渡した情報だけで、その仕事を知らない人が正しく使えるか
